# Command guide

The generated [command reference](commands/) is canonical for command syntax and flags. This companion preserves cross-command operating guidance that cannot be generated from a single Cobra help string.

## Setup and safe application

`dot init --from <file>` pre-populates identity from another machine, while workspace path and terminal are confirmed locally. Setup covers identity, timezone, profile, GPU detection, module opt-ins, SSH key, workspace repositories, vault location, and GitHub authentication.

For a cautious apply, run `dot preflight --check-only`, `dot preflight`, `dot check`, and `dot apply --dry-run` before a selected module. Files are backed up under `~/.local/share/dotfiles/backup/` before overwrite; an identical SHA256 is not overwritten. `dot config export <file>` creates the portable YAML consumed by `dot init --from <file>`. `dot update` verifies the release checksum and binary; use `dot ai update` for AI CLIs and plugins. From v2.70.29 or earlier, run the curl installer once instead: those updaters refuse a binary over 16 MiB (#231). A Homebrew install updates through its owning brew and reloads dot LaunchAgents that run the new binary (#235): exact verified native tap recipes use the bounded prebuilt admission path, while changed or stale metadata uses the full maintenance gate and `brew update` only when the tap lags. `dot update --homebrew` lets a standalone dot binary target that managed install.

## Secrets and migration

`dot secrets restore` decrypts to a 0600 temporary file and atomically renames it into place. A differing target is retained as `<dest>.bak-<timestamp>`; identical files remain unchanged. One-stop backup and restore coordinate profile, apps, AI, and secrets, can run `dot apply` after profile state, and retain pre-restore copies.

## Workspace commands

`dot open` requires an explicit subcommand, so `dot aply` cannot accidentally create a project. `dot layouts` offers `dev`, `claude`, and `monitor`; `dot doctor` reports tool paths and optional-tool availability.

For dev builds (no ldflags), `dot version` falls back to Go's embedded VCS info with a `-dirty` suffix if the working tree has uncommitted changes.

## Cleanup and indexing

`dot clean` always protects `_sys/`. Its safe set includes node modules, Python caches/environments, `.next`, `.cache`, and `.DS_Store`; `--all` adds `dist`, `build`, `out`, and `target` because those can hold deliverables.

`dot noindex` walks project roots but marks cache roots at the top. `~/.claude` is excluded so plans and skills stay searchable. `build` and `out` are not marked because finished deliverables need to be findable. A marker affects only future Spotlight indexing; use `sudo mdutil -E /` to remove existing entries.

## Tunnel operations

`dot tunnel setup` renders explicit `--config /etc/cloudflared/config.yml tunnel run` arguments, avoiding the macOS service-install form that omits the run command. Cloudflare Access policy creation stays in the dashboard; then run `dot tunnel client add <hostname>` on clients.

## Watchdog operation

`dot watchdog` ships disabled in every profile; a host opts in with `watchdog.enabled: true` and `dot watchdog setup`, which writes a resolved config snapshot to `~/.local/state/dot/watchdog/watchdog.yaml` and loads the user LaunchAgent `com.dotfiles.watchdog.reap`. The scheduled `dot watchdog reap` reads only that snapshot, so profile edits take effect on the next `setup`, not the next pass. "Sustained" CPU is measured across runs via `samples.json`, keyed by PID plus process start time so PID reuse cannot inherit a streak, and a below-threshold sample resets it. `dry-run` mode only logs and notifies; `enforce` sends SIGTERM, waits `kill_grace`, then SIGKILLs. Every candidate and kill lands as a JSON line in `~/Library/Logs/dot/watchdog.log`; `dot watchdog log [N]` tails it. `dot watchdog uninstall` removes the LaunchAgent; deleting state and logs is an interactive-only prompt that `--yes` never auto-confirms.

With `watchdog.warp.enabled: true`, setup also installs the root LaunchDaemon `com.dotfiles.watchdog.warp` (the daemon restart needs the system domain; setup primes sudo and refuses when the Cloudflare WARP daemon is not in `launchctl list`). Each `dot watchdog warp` pass counts health as `warp-cli` Connected AND an interface address in 100.96.0.0/12. After `fail_threshold` consecutive failures it runs `warp-cli disconnect && connect` (up to 3 attempts), then `launchctl kickstart -k` the WARP daemon, rate-limited to one restart per 30 minutes; the bookkeeping lives in `warp.json` and every action is logged and notified. `dot watchdog setup --headless` (requires `watchdog.power.headless: true`) saves the current `pmset`/`systemsetup` values to `power.json` BEFORE applying `pmset -c sleep 0`, `pmset -a autorestart 1`, `pmset -a womp 1`, and `systemsetup -setrestartfreeze on`; uninstall removes the warp daemon and offers to restore those values under the same interactive-only prompt style as the state deletion. `dot watchdog status` also reports the heal daemon, live WARP health, and whether the `dot tunnel` cloudflared daemon is installed — the independent SSH path a remote host should carry.

With `watchdog.monit.enabled: true`, setup ensures the `monit` binary (offering `brew install monit` when missing), renders `~/.config/monit/monitrc` (0600), and loads the user LaunchAgent `com.dotfiles.monit`, which keeps monit running in the foreground on a 60-second cycle with its web UI off. The monitrc alerts through `dot watchdog notify warn` when loadavg(5min) exceeds `load1_threshold` (default: the host's logical CPU count) or cpu(user)/cpu(system) exceed their thresholds (defaults 90%/50%) for `cycles` consecutive checks (default 3), logging to `~/Library/Logs/dot/monit.log`. When `watchdog.monit.screensharing` is on (the default), setup asks — before rendering the monitrc — whether to install, with sudo, the root-owned helper `/Library/Application Support/dot/screensharing-heal` plus a `/etc/sudoers.d/` grant (validated by `visudo -c -f`) letting the user run exactly that helper passwordless; monit's `check host screensharing` then kickstarts `com.apple.screensharing` when the VNC handshake on 127.0.0.1:5900 fails, and declining the helper leaves the check out of the monitrc entirely. `dot watchdog status` reports the monit binary, the agent's loaded state, and monitrc drift against the snapshot; uninstall removes the agent and monitrc, and offers the root helper and sudoers removal under the same interactive-only, default-No prompt as the power restore.

With `watchdog.beszel.enabled: true`, setup adds the Beszel external-monitoring agent: it verifies `watchdog.beszel.hub_url` is set and the env file `~/.config/beszel/agent.env` exists BEFORE any Homebrew prompt — a missing hub URL or env file skips the step with a warning, since the env file carries the hub KEY/TOKEN and arrives via `dot secrets restore` — then ensures the `henrygd/beszel/beszel-agent` Homebrew formula (homebrew-core carries no `beszel-agent`) and installs the user LaunchAgent `com.dotfiles.beszel-agent`. The unit is deliberately dot-owned rather than a `brew services` unit: it runs `/bin/sh -c 'set -a; . "$HOME/.config/beszel/agent.env"; set +a; export LISTEN="${LISTEN:-<listen>}"; exec <agent binary>'` so the secrets-managed env (HUB_URL/KEY/TOKEN/LISTEN) is injected at start, with `watchdog.beszel.listen` (default `:45876`) only the fallback — an env-file LISTEN wins over the config value. A custom `watchdog.beszel.env_path` works the same way but is NOT covered by `dot secrets` backup/restore (only the default path is a registered secrets pair); setup says so and its missing-file skip asks for manual placement instead of `dot secrets restore`. `dot watchdog uninstall` removes the plist while always keeping the env file. `dot watchdog status` reports the hub URL from the snapshot, env file PRESENCE only (never contents), the plist state, and the agent binary. Alert rules — agent offline ≥ 5 minutes, CPU > 80% for 10 minutes, elevated load average — are configured on the external Beszel hub itself; hub-side alerting is an ops concern, not config dot ships.

With `watchdog.notify.telegram.enabled: true`, the watchdog notifier gains a third channel beside macOS (`macos`) and ntfy (`ntfy_url`): a Telegram Bot API `sendMessage` POST. The bot credentials never live in the tracked profile or the synced workspace — they are read, lazily at every send, from the secrets-managed env file `~/.config/dot/telegram.env` (a registered `dot secrets` pair; KEY=VALUE lines, `#` comments and an optional `export ` prefix tolerated) holding `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`, with the same-named process environment variables winning over file values. `watchdog.notify.telegram.env_path` relocates the file (a custom path is not covered by `dot secrets` backup/restore), `reminder_interval` (default 30m) is the minimum time between repeat alerts while a failure persists, and `quarantine_threshold` (default 0, off) caps how many quarantined deletions one peer run may move before warning. Enabled-but-unconfigured (no credentials in the file or the environment) is a clean no-op; a configured channel that fails to send is an error, matching the existing notifier contract.

## Resource admission

`dot admit` enforces the workspace resource policy at per-repo granularity: one heavy job (build, full test, indexing, bulk copy, dependency update) per project repo at a time — the scope is the repo's git common dir, so all worktrees, branches, and sessions of one repo share a single slot — while different repos run in parallel subject to the pressure gate. `--class maintenance` takes the one host-wide maintenance slot for global tool installs/updates instead. The gate snapshots memory pressure level, the macOS thermal state (`NSProcessInfo.thermalState`), load1, and CPU idle (macOS; Linux reads /proc), plus the newest WindowServer reports in `/Library/Logs/DiagnosticReports` and `~/Library/Logs/DiagnosticReports`, each with its `Retired/` subfolder (a report whose name contains `watchdog`, or an `.ips` with a `WATCHDOG` termination; the system folders are readable only by admin accounts, so on a standard account the scan stays incomplete and the gate defers), and defers on warn/critical memory, a serious or critical thermal state, idle below 15% or load1 at or above the CPU count sustained 60s, or a WindowServer watchdog termination inside its 30-minute grace (pre-boot evidence is suppressed). Every probe carries an availability flag: failed or missing telemetry defers — the gate is never false-healthy. Once an episode opens, recovery needs five continuous minutes of normal memory, idle at or above 30%, and load1 below 70% of the CPU count before the gate admits again. Slots are atomic `mkdir`s holding a lease (`owner, session, pid, pid_start, pgid, class, cwd, acquired_at, heartbeat_at, deadline`); a 30-second heartbeat keeps the lease alive, and a crashed owner is reclaimed only after the heartbeat expires AND the pid+start incarnation is verifiably gone (a fresh heartbeat is never force-freed, so PID reuse cannot steal a slot). A child `dot admit` under `DOT_ADMISSION_SCOPE` for the same scope/class runs without re-acquiring. On defer the exit is 75 with a JSON outcome under `--json`, and the alert goes through the watchdog notifier at most once per defer episode per scope. `dot admit status` shows active owners, per-probe availability, the last WindowServer event, and the hysteresis countdown — and always notes that jobs launched outside `dot admit` and `dot ai run` hold no lease, and a bounded process-table scan (the one `dot ai run` used) defers when such heavy work runs in the same repo or its repo is unknown. State lives in `~/.local/state/dot/admission/`; the controller never terminates processes — deferral, not enforcement, is the mechanism.

The only update allowed a warning-memory exception is `dot update` for an exact, checksum-verified native release. It still reserves the maintenance slot and requires 30 seconds of fresh healthy telemetry with no swap activity; samples may be no more than 45 seconds apart. It remains blocked on critical/unknown memory, serious/critical thermal state, recent WindowServer watchdog, CPU idle below 30%, load1 at or above 70% of CPU count, missing telemetry, or any swap change. This decision uses separate history and does not modify heavy-work admission history. The archive is bounded to 32 MiB compressed; it contains one root `dot` executable up to 64 MiB and may contain root `LICENSE` and `README.md` documents up to 1 MiB each. The entire expanded gzip stream, including tar metadata and padding, is capped at 67 MiB; `checksums.txt` is capped at 1 MiB. For Homebrew, the installed binary and keg version, raw trusted-tap recipe, native URL, SHA-256, target version, and unpinned state must match; the canonical recipe has no dependencies or post-install hook. Dot rechecks the raw recipe, pin, and installed binary before and after admission, then checks the version Homebrew installed. Any unverified recipe or stale metadata uses the full maintenance gate. `dot update --homebrew` lets a standalone binary target the existing managed formula through Homebrew, without writing the Cellar directly. Other refreshes, installs, and tool updates remain under the regular gate.

## Guard operation and limits

`dot guard` edits only entries marked `# dot-guard`; a semantic rewrite may sort JSON keys but does not alter other values. `enable` and `disable` apply to new Claude Code sessions, while `freeze` and `unfreeze` update live state.

The hook fails open if the dot binary is missing or moved. `dot guard status` reports that condition, and `dot guard enable` must be re-run after moving the binary. It is a guardrail, not a sandbox: it only inspects the Bash tool and shell writes are outside the freeze boundary.

## Sync and peer operating model

`dot sync` sends a Git-aware union: root-repository tracked files plus approved untracked binary extensions, minus submodules, junk, and deny-by-default secrets. `allow.txt` records an explicit secret exception. A baseline-unknown mirror file stages under `inbox/gdrive/` for manual routing. The baseline also records every file a mirror push sent, even when rsync then stops with an error (a `--max-delete` stop comes after every transfer), so a file a live process removes while the push runs is a workspace deletion on the next push rather than a baseline-unknown mirror file. A push that leaves a planned deletion in the mirror fails. Local mirror pushes with delete propagation select rsync 3.x from PATH or the Homebrew fallback paths. Delete propagation refuses before any transfer when no modern client is available (`brew install rsync`); pushes without deletes can still use an older client. Status shows the selected binary path and version. A deletion can still remain after an I/O error or because a filter protects the name. `dot sync status` shows `Push stalled` when the last push run refused (a preflight block such as a missing mirror included, a pause excepted) or failed, or when the scheduler is on and no push completed within three intervals; a run that skipped files after an error (rsync exit 23) does not count as completed.

Run `dot sync names normalize --profile=peer --dry-run` and then `--yes` for selected NFC-to-NFD names. It refuses invalid UTF-8, symlinks, and canonical collisions, moves deepest paths first, and rolls back completed moves on error. Names Dropbox and Windows cannot store (a segment ending in a space or period) are excluded from push plans and uploads; a mirror-only copy of such a name that the baseline proves the workspace put there (left by a rename) is a leftover, which a push with delete propagation moves into the workspace's `.sync-conflicts/<ts>/from-mirror/` when there are no more than `max_delete` of them (a budget apart from the push's own deletions). Any other mirror-only path with such a name may be a cloud file and is only listed. A push never sends symlinks, so a workspace file replaced by a symlink is treated like a deletion. With delete propagation on, the push moves the mirror copy into the same `from-mirror/` folder while the baseline proves it; an unproven copy is a conflict that only `--mode=force` moves. `dot sync names trim --dry-run` and then `--yes` renames the trailing-whitespace ones under the same preflight and rollback rules. Profiles use stores below `<workspace>/.dotfiles/<profile>/`; the peer profile shares the cloud workspace lock while other custom profiles do not.

`dot peer` is two-way peer sync, not the cloud mirror. Its deletion propagation quarantines baseline-recorded removals. Host paths split by list: entries in `home-paths-tracked.txt` get the same baseline-aware semantics (deletes propagate, simultaneous edits quarantine the losing payload under `~/.dot-peer-conflicts`), while entries left in `home-paths.txt` alone stay additive with newest-mtime wins — `.claude.json` included. `dot peer init` and `dot peer setup` seed the tracked list, with the Claude auto-memory entry included only when both machines share the workspace path. Keep the same dot version on both machines before scheduling because older peers do not understand tombstones. The coordinator records simultaneous conflicts in `peer-conflicts.log`; an offline peer exits zero for safe scheduled laptop runs.

With Telegram alerting on (above), `dot peer sync` reports its outcome through the watchdog notifier's transition/rate-limit alerter: a real transfer or safety-refusal error alerts critical, a two-way run that holds destructive transitions (baseline unchanged) warns, a complete run quarantining more deletions than `quarantine_threshold` warns, and the first complete run after an episode sends one recovery message. One message fires at the ok→fail transition, then at most one reminder per `reminder_interval` while the condition persists; the episode state lives in `<workspace>/.dotfiles/peer/alert-state.json`. The designed-clean shapes — an unreachable peer, a fence demotion, a lost scheduled lock race — never alert. `--dry-run` sends nothing and writes nothing. An alert delivery failure is a stderr warning and never changes the run's exit code, error, or baseline semantics.

Peer host paths exclude `known_hosts`, `~/.maru/env`, plugin caches, `~/.codex/auth.json`, and `~/.codex/config.toml`: they are trust, absolute-runtime, or keychain-coupled state rather than portable workspace settings.

## AI helpers and portability

`dot ai` manages helper files and portable AI configuration, not GUI app installation; use `dot apps install` for casks. The `*-yolo` helpers forward full-access flags and belong only in trusted workspaces. HUD apply owns only the `# dot-hud` Claude statusLine. A foreign owner is a conflict unless `--force` is supplied; `--persist` records the desired HUD.

Portable AI snapshots exclude skill roots, auth by default, caches, histories, databases, and machine-local plugin state; archives reject symlinks, hardlinks, devices, and link-pivot paths. `~/.codex/config.toml` is normally kept live on restore because Codex rewrites it and hashes MCP credentials into the Keychain. `dot ai skills` is diagnose-only: Maru owns runtime skill symlinks and tool federation.

## amem and the claude-mem retirement

`dot ai memory install|status` register amem's MCP server for Kiro and Copilot and report its health (`dot` never installs amem; `amem setup` registers Claude Code, Codex, Kimi, Qwen, pi and Antigravity). `dot ai memory retire-claude-mem` is a dry run unless `--apply` is given; see the README. The former `dot ai memory sync|update|bridge` commands and the hourly peer sync LaunchAgent are gone: amem syncs through its own git refs and has no resident process.

## Apps and profile snapshots

`dot apps` manages cask installation and per-host settings. A profile snapshot contains config, install and backup lists, metadata, and optional age keys at `<backup-root>/profiles/<hostname>/<version>/`.

## Backup-root resolution

`dot apps`, `dot profile`, and `dot ai` share this precedence: an explicit command flag, saved `BackupRoot`, a cloud root detected from a `secrets/` marker, then the local default. It spans commands and has no generated page.

## Global flags

All commands inherit `--config`, `--dry-run`, `--home`, `--module`, `--profile`, and `--yes`. Generated pages carry the inherited option block.
